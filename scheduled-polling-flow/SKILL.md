# 定时轮询与多条件判断工作流

## 这套流程解决什么

定时轮询的线上事故几乎都集中在三处：**重复触发、上游滞后、条件判断漏了兜底**。这套工作流把「调度」「触发」「校验」「异常处理」拆开设计，让你在设计阶段就把幂等、时限、降级想明白，而不是等线上出现重复扣款才发现。

一句话：**先设计异常路径，再写正常路径。**

## 七个设计动作

### 1. 定义任务表

- 列出所有要被轮询的对象、期望频率、优先级。
- 分清：哪些必须近实时、哪些可以批量、哪些根本不需要轮询。

**产出**：任务表。

### 2. 设触发点与校验点

- 触发：定时器 / 事件 / 手动。
- **校验（check valid）**：每次拉到的数据是否可用于后续动作——新鲜度、完整性、合法性。校验不过就不往下走。
- 校验点要明确：校验什么、不过时是跳过这一轮还是停下告警。

**产出**：一次轮询的准入条件。

### 3. 统一调度与去重

- **只有一个调度源**，避免多节点同时拉同一份数据。
- 写清并发控制、超时、重试策略。
- 多实例部署时，明确用锁 / 选主 / 幂等键中的哪种来保证同一任务不被同时执行。

### 4. 多条件判断：决策矩阵

把「什么条件下做什么」写成表，不要散在一堆 if-else 里：

```text
| 条件组合 | 判定 | 动作 | 备注 |
| --- | --- | --- | --- |
| A 且 B |  |  |  |
| A 且非 B |  |  |  |
| 无匹配（默认） |  |  | ← 必填 |
```

必须明确三件事：

- **优先级**：多个条件同时满足时，谁先。
- **默认分支**：没有任何条件匹配时做什么（最容易漏，也最容易出事故）。
- **冲突裁决**：条件互相矛盾时按什么原则处理。

### 5. 三类硬约束

- **幂等**：重复触发或重复拉取不能造成重复动作（重复下单、重复扣款）。用幂等键 + 唯一约束 + 加锁。
- **时限**：数据超过某个时点即失效。过期数据不得再用于成交或不可逆动作。
- **精度**：金额与数量的精度不能丢（浮点 vs 定点）。

### 6. 失效模式与退路

| 什么情况会坏 | 怎么发现 | 怎么退 |
| --- | --- | --- |
| 上游数据滞后 | 监控告警、结果长时间不变 | 降级为不自动动作，或熔断该轮 |
| 重复触发 / 多实例并发 | 对账发现重复记录 | 幂等键去重、加锁、选主 |
| 轮询间隔与上游更新频率不匹配 | 拉到的总是旧数据 | 调间隔，或改事件驱动 |
| 落入空分支 | 无动作或抛异常 | 补默认分支 + 告警 |
| 调度器单点故障 | 整体停摆 | 只读降级 + 人工兜底 |
| 校验点被跳过 | 脏数据进入了成交/写库 | 校验前置 + 拒绝而非忽略 |

**监控要能区分「没数据」和「数据没变」**——这两者需要的处置完全不同。

### 7. 沉淀

- 记下这次轮询的任务表、校验规则、条件矩阵、硬约束与退路。
- 提炼：这类轮询里最容易坏的是哪一环？下次设计前先怀疑什么。

## 关键规则

- **先异常路径，后正常路径**：这类系统 60% 的风险都在异常路径上。
- **兜底动作必须安全**：拿不准就不动作，不要默认往前推进。
- **不可逆动作要加双重闸门**：金额上限、次数上限、人工确认点。
- **校验不过就拒绝**：不要「校验失败但还是用了」。

## 边界

- 涉及资金或下单的轮询，任何自动动作都要有幂等与上限。
- 拿不到可靠上游数据时，宁可停下等人工，不要靠猜。
- 不要为了「实时」而无限缩短轮询间隔；频率受上游能力和限流约束。
