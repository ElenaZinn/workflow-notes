# Bug 修复工作流

## 这套流程解决什么

修 bug 最常见的失败不是「改错了」，而是**跳步**：看到现象就开始改，改完没效果，再改，反复几轮后连最初的现象都记不清了。

问题出在把「定位根因」和「动手修复」混在一起。这套工作流把两者严格分开，每一步都有可交接的产出物。

核心原则：**在拿到明确根因之前，任何改动都只是试错。** 试错不是不能做，但要清楚它只是权宜，不能当成定位。

## 七步流程

### 第 1 步　问题定格与优先级

- 现象：是什么、在哪里出现、什么条件下出现、必现还是偶现。
- 优先级：阻断性的（崩溃、数据错误、资金相关）和体验性的（卡顿、文案）投入完全不同。
- 定格：给出最小复现路径；如果暂时不能复现，就明确写出已知触发条件与观察到的规律。

**产出**：一句可验证的问题描述 + 优先级。

**常见跳步**：拿一句模糊描述（「就是有点卡」）就动手。问题没定格，后面所有结论都不可信。

### 第 2 步　收集证据，定位根因

- 先取数据再下判断：日志、堆栈、Profiler/Perfetto、网络抓包、链路追踪、埋点、二分定位。
- 区分「表象」和「机制」。表象是「卡顿」，机制是「view 与 state 各消费了一次点击事件」。
- 一次只验证一个假设：做一个检查去证实或否证它，不要同时猜五个原因。

**产出**：证据（数据、火焰图、日志）+ 一句机制层的根因陈述。

**常见跳步**：凭经验断言根因，拿不出证据。没有证据的根因判断后面会以「改了没效果」的形式回来。

### 第 3 步　画时序图与调用链

- 画事件时序：谁在什么时刻触发了什么。
- 标出调用链：每一环由谁负责、哪一环偏离了预期。
- 跨模块、跨端、跨线程的问题必须走到这一步，否则改动点会划错位置。

**产出**：一张时序图或调用链，并明确标出偏离点。

**常见跳步**：跳过画图直接改。时序图是「定位改动点」的前置条件，不是可选动作——它也是能拿去和同事对齐、请人给第二意见的东西。

### 第 4 步　定位改动点

- 改动点必须能反向指回第 2 步的证据和第 3 步的偏离点。指不回，说明还没定位准。
- 一个 bug 通常只有一个主要改动点。如果方案要改五个地方，大概率是没找对。
- 明确影响半径：改这里会波及谁、有没有别的调用方。

### 第 5 步　出修复方案

- 写清：改什么、为什么这样改、预期效果、副作用（回归风险）。
- 小步可回滚：优先能单独验证、能撤回的改法。
- 涉及稳定契约的改动（公共接口、数据格式、对外协议、并发语义）先确认，不要顺手改。

### 第 6 步　修复未生效时的排查顺序

**这一步最容易漏，但它是「能修好」和「修不完」的分界。** 改动后问题仍在时，按顺序排查，不要盲目再改：

1. **核对改动有没有生效**：代码真的跑到了吗？编译、缓存、环境、灰度范围对吗？
2. **复核根因**：原来的证据还支持这个结论吗？是不是漏了并发、时序、环境差异。
3. **换假设**：换一个方向重新做一次检查（回到第 2 步），而不是在原方案上加码。
4. **换人或升级**：找第二意见，或升级到掌握更多信息的人。
5. **临时缓解**：短期定位不了，先用最小代价缓解（加日志、加兜底、降级），并留下待办，不要硬撑。

### 第 7 步　复盘与沉淀

- 留下：现象、证据、根因、改动点、方案、结果。
- 提炼：这属于哪一类失效模式？下次遇到类似现象该先怀疑什么？
- 归档：用 `references/bug-record-template.md` 写成一条可被未来检索的记录。**「卡住的地方」就是最值钱的一栏。**

## 关键规则

- **先分级再处置**：优先级决定投入，不是所有 bug 都用同一力度。
- **先有证据再下结论**：任何改动都应能指回第 2 步的证据。
- **留痕**：每一步的产出物都要能交接给下一个人或下一次的自己。
- **改不动就换假设**，不要在错误方向上加深投入。

## 失效模式

| 失效 | 表现 | 怎么退 |
| --- | --- | --- |
| 根因误判 | 症状相似但原因不同，改了没效果 | 回到第 2 步重新取证据 |
| 回归副作用 | 修好这个，弄坏别的 | 补回归验证，缩小影响半径 |
| 改动未生效 | 方案对但没生效 | 先核对是否真的执行了 |
| 反复复发 | 同一个 bug 又出现 | 只缓解了表象，回第 2 步找机制 |
| 过度修改 | 小问题改了大架构 | 回到「改动点唯一」原则 |

## 边界

- 不为走流程而走流程：单行 typo 这类确定性修复可以直接改，但仍要留下一句记录。
- 不夸大确定性：证据不足时明确写「暂未证实」，不要写成结论。
- 涉及生产数据的排查动作，先在安全环境做。
- 迁移或重构过程中发现的旧 bug 默认只记录、不顺手修，避免无法区分「新引入」还是「本来就有」。
